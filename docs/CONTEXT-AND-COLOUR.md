# Application context and independent backgrounds · Beta

The existing AppBar, dock, Shell reservations and connected expansion geometry are retained. Click the active application name to reveal contextual actions. The resting header stays compact; up to eight actions are shown initially, with More actions inside the same expansion. Unsupported actions are omitted, and Refresh available actions requests fresh discovery.

## Identity and targeting

`ActiveApplication` coalesces out-of-context WinEvents for foreground, focus, visibility, destruction, state and name changes. It samples `GetForegroundWindow`, not a process-name guess. Window identity includes HWND, owning PID and process creation time. Distinct windows in one process remain distinct targets. `GetAncestor(GA_ROOT)` scopes child events without replacing an owned foreground dialog with its owner. `GetWindow(GW_OWNER)` helps exclude unrelated tool windows. Invisible, cloaked, no-activate, desktop/taskbar and known Shell helper windows are filtered.

`ApplicationIdentity` uses `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`, `QueryFullProcessImageName` and `GetApplicationUserModelId`. An ApplicationFrameWindow's child processes are inspected to resolve the packaged content application, while commands continue to target the actual frame HWND. Names prefer the Shell app catalogue, then executable description, then the window title. Package Shell icons and bounded WM_GETICON/class-icon lookup preserve application/window branding. Failure to read an executable no longer makes a visible application disappear. Restricted process identities can be displayed using their title, but actions requiring unverifiable process creation identity are refused.

While New Start owns focus, only the last live, visible, non-minimised external window is retained. Closing/hiding/minimising it invalidates that target. Desktop focus clears the application. UIA actions revalidate HWND/PID/creation time, the exact accessibility runtime ID, name, type, enabled state and actual foreground window. A focus/context change cancels pending discovery/execution. No process injection, elevation, UIAccess signing or security bypass is used.

## Capability providers

`ApplicationCapabilities` owns context, availability, bounded caching and execution. `ApplicationCapability` normalises navigation, editing, search, window, media and additional adapter actions. `CapabilityRegistry` recognises explicit accessible command names and a small set of semantic navigation automation IDs; it never treats an app category as proof of a command. Current name recognition is principally English. Localised/renamed or inaccessible commands may be absent.

UI Automation runs on an MTA thread in a hidden instance of the same executable. Discovery examines at most 300 control-view nodes, depth eight, with bounded siblings, a 1.6-second traversal budget and a 2.6-second parent-enforced process timeout. A hung provider can therefore be terminated without blocking the AppBar or accumulating stuck client threads. Individual incomplete nodes do not discard discoveries elsewhere. There is no permanent full-tree scanner. Cache keys are per-window identities, limited to 32 entries and 12 seconds on context reuse; relevant WinEvents invalidate them and coalesce rediscovery. Explicit refresh handles providers that fail to publish state events.

The worker checks Invoke, Toggle, Selection, SelectionItem, Value, RangeValue and ExpandCollapse support. Only established executable operations become actions. Search/Find edit controls can receive focus; their values are not read or overwritten. Selection/range/value patterns are recorded as supported mechanisms, but arbitrary app-specific values or selection changes are not guessed. MSAA default actions are available through `AccessibleObjectFromWindow` for native HWND controls whose accessible name/default action/state can be verified. This is a bounded compatibility fallback, not a claim to enumerate every legacy object hierarchy.

Standard window commands use Win32 and retain existing AppBar controls. System Media Transport Control actions are associated only with a matching source application identity, then use the session's supported commands. A failed operation reports failure, rather than simulating success. No keyboard shortcuts are sent.

`IApplicationCapabilityAdapter` supports both accessibility recognisers and optional asynchronous dedicated API discovery/execution. Provider failures/timeouts are isolated. Dedicated API actions take priority over generic duplicates. Future providers must honour cancellation, revalidate their application target and supply truthful availability; they do not require changes to the expansion engine.

The Chromium adapter supports exposed Back, Forward, Reload and New tab Invoke controls. ChatGPT's adapter recognises exposed New chat, Search chats and sidebar controls when present. Neither forces hidden accessibility content or uses internal endpoints. In the tested ChatGPT window no supported commands were exposed, so only window management is available. Advanced Chrome tab integration would require an opt-in extension and a registered native messaging host with explicitly scoped permissions; none is installed by this change. ChatGPT's documented companion-window shortcut is not a general window-scoped app command API and is not sent blindly. No credentials or OpenAI API integration are introduced.

## Background settings

Appearance contains the same reusable background editor for Dock and AppBar. Each independently supports System, Custom, Wallpaper automatic and Wallpaper palette, RGB sliders, six-digit HEX entry, preview, recommended swatches, transparency, blur and reset. Selecting a swatch freezes that selected colour in Wallpaper palette mode; automatic mode follows either the dominant or accent cluster. Dock background remains optional and off by default. Start/standalone menus retain their existing separate settings.

System colour uses Windows **application** Light/Dark mode, or New Start's explicit theme override: opaque dark is #000000 and opaque light is #FFFFFF. Background alpha is `1 - transparency`: 0% is solid, 50% preserves the selected RGB at half opacity, and 100% removes the material tint and native blur. Icons/control opacity is not changed. Native blur is also disabled behind a fully opaque surface, so Acrylic/Mica cannot introduce a grey opaque fallback. If native effects are unavailable, the same alpha/colour contract still applies, with no blur. Windows high contrast intentionally uses the system accessibility surface/foreground.

The resting AppBar and attached expanded lobe share one material and one colour resolution. Selected RGB is part of the material cache key. Foreground black/white is chosen by linear-sRGB relative luminance against the selected colour composited over the wallpaper's representative colour. User-selected backgrounds are never silently replaced. At high transparency the actual underlying application may differ from the wallpaper estimate; users can reduce transparency for stronger contrast. A near-transparent input mask preserves the existing bar hit-testing; the background material itself has zero alpha at 100%.

`WallpaperPalette` resolves per-monitor files through IDesktopWallpaper monitor device paths/rectangles, with SystemParametersInfo fallback when no per-monitor image can be read. Sampling decodes a small image, then performs deterministic weighted-RGB k-means clustering. Dominance uses cluster population; accent combines separation, saturation and population. Swatches are actual image-derived cluster representatives, without invented complementary filler. Monochrome images can yield one swatch.

Wallpaper/display/user-preference notifications are debounced. Static and Windows-exposed slideshow changes refresh paths; there is no continuous screen capture. Memory cache is bounded to 32 analyses; local disk palette cache keys include path, modification time and length. Each AppBar resolves its own monitor; the existing single-dock placement is unchanged. Missing/inaccessible images retain the previous palette/selected fallback. Dynamic wallpaper applications that do not expose static wallpaper files are unsupported. Cache/settings files remain local and are excluded from publication.

Existing menu settings migrate once into independent Dock transparency/blur fields; pins, layout and all other preferences remain intact. Invalid sources, colours and numeric values are normalised. Changes save immediately and are restored on launch.

## Validation and limits

The interactive `--verify-context-appearance` fixture verified two windows in one process, foreground switching, closure, actual UIA Invoke execution, disabled-control omission, search focus discovery, wrong-foreground rejection and a deliberately unresponsive provider timeout. It also verified solid/tinted/clear alpha, independent persisted colours, migration, invalid data, contrast, dominant/accent clustering, a monochrome palette, file-change invalidation, cache reuse and missing files. Its Run checks button supplies real foreground permission instead of bypassing Windows activation restrictions.

`--verify-capability-inventory` is read-only and can run beside New Start. This pass resolved names and icons for Explorer, Chrome, Edge, ChatGPT, Windows Settings (hosted packaged content) and WhatsApp (WinUI/custom frame). It discovered exposed navigation in Explorer/Chromium and search focus in Settings; some packaged apps exposed no supported actions. No commands were executed against personal apps. Visual checks confirmed Chrome/Explorer tracking, swatch selection, a tinted continuous expansion, opaque black, and clear material. Edge interactive switching was not completed because the UI test tool could not establish its browser URL; identity/icon/discovery were checked through the product's read-only diagnostics.

AppBar and Dock material/reservation regressions and the existing audit/pin checks remain available. Only one physical display/DPI configuration was available in this pass. Live mixed-DPI/per-monitor wallpaper changes, OS theme toggling, elevated/protected apps, MSAA-only vendor controls, extended uptime and driver variations still need broader hardware acceptance. Windows UIPI, provider incompleteness, secure desktops and foreground activation rules remain real boundaries, not bypassed features.
