# Contextual application menu · Beta

The optional AppBar application-menu strip uses the existing foreground identity and killable accessibility-worker service. It exposes only actual, enabled, visible expandable UI Automation MenuItems belonging to an application's MenuBar. Native title-bar System menus are excluded. Applications that expose no suitable menu bar keep their ordinary capability panel; categories are never invented from the app's type or process name.

Discovery is passive. A user click on a discovered category lazily opens that specific menu through ExpandCollapsePattern, snapshots supported visible commands, then collapses the menu opened for inspection. It may briefly activate the target application because many native menu providers require foreground access. The AppBar ignores deactivation only while `ApplicationCapabilities.MenuTransition` is true. The worker returns focus to the previous New Start window only if focus still belongs to the application inspected, avoiding unrelated-window focus theft.

The returned menu actions carry the category's persistent runtime ID and a verified accessible-name path. Commands reopen that category, resolve each submenu path, check the current PID/creation identity, foreground, enabled state, exact name and control type, and execute a currently exposed Invoke, Toggle, Expand or verified MSAA default action. Transient popup runtime IDs are not reused as command targets. Ambiguous paths fail with feedback rather than choosing an arbitrary matching command. No guessed keyboard shortcuts, application-specific private endpoints or process injection are involved.

The same out-of-process timeout boundary protects the AppBar from blocked UIA/MSAA calls. Category scans remain bounded to the existing 300-node discovery budget; menu snapshots/path lookups use smaller bounded traversals. Per-app categories update with foreground changes. Metadata/focus invalidations clear or refresh stale generic capabilities; command execution always revalidates the current menu. The implementation supports classic menu providers and providers that expose expandable menus under WinUI/custom frameworks; browser hamburger menus that do not expose MenuBar categories are intentionally omitted.

`ApplicationCapabilities` provides `MenuCategories`, `MenuActions`, `SelectedMenuCategory`, `MenuTransition` and asynchronous `OpenMenu(category)` for the host. `Execute(action)` handles leaf actions or submenu expansion. The host retains its connected AppBar expansion and renders these actions with the shared appearance/context-menu infrastructure. Submenu actions with `Method == "Expand"` keep the panel open; leaf execution may collapse the panel so the application or its resulting dialog receives interaction.

`ApplicationMenuValidation.Fixture(token)` supplies a disposable real WinForms MenuStrip with File/Edit/View/Help, a disabled command and a nested submenu. `Run()` checks real category discovery, non-executing inspection, actual Save/submenu action execution and stale identity rejection. Its Run button gives normal Windows foreground permission; it does not bypass activation restrictions. Reports remain local and can contain accessible menu labels, which must be reviewed before public sharing.

Limitations: accessibility coverage, localisation and custom menu providers vary. Categories are taken from actual menu labels, so translated native categories can be displayed, but providers without MenuBar/ExpandCollapse support remain unsupported. A slow or unavailable provider produces feedback and preserves window controls. This is not a replacement file explorer or a claim that every application exports its complete menu system.

Implementation references: Microsoft's [MenuItem contract](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportmenuitemcontroltype) makes action patterns conditional on the menu item's actual function; [MenuBar guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportmenubarcontroltype) defines the accessible category hierarchy. The separate MTA worker follows Microsoft's [UI Automation threading guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading), keeping external accessibility calls off New Start's UI thread. The timeout/process boundary is New Start's protection against a provider that fails to return.

For a requested action New Start uses [AllowSetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow) to delegate its existing foreground permission to that specific helper process. This does not disable foreground locking or grant permission to arbitrary processes: Windows rejects the delegation when New Start cannot set foreground itself, and the worker separately verifies the requesting/target foreground identity before acting.

The helper observes the requested foreground window for a bounded 200ms after activation. This acknowledges Windows' [asynchronous cross-input-queue activation](https://devblogs.microsoft.com/oldnewthing/20161118-00/?p=94745) instead of rejecting a valid request on an immediate read. It makes one activation request, stops if another external window takes foreground, and never attaches input queues.

Validation entry points are `--verify-application-menus` (interactive disposable fixture) and `--verify-interactions` (wheel handling, independent Start-button migration, advanced-setting validation and editor navigation/reset checks). Both run before the normal single-instance and shell-recovery paths. They do not load or save the user's preferences or change the running Dock/AppBar. Local reports are `application-menu-verification.json` and `interaction-verification.json` in New Start's local application data directory.

Validation checkpoint, 16 November 2026: the live menu fixture passed all nine checks, including actual Save and nested Plain text command execution, real category discovery, safe inspection, disabled-command omission, stale identity rejection and submenu discovery. This exercise exposed and verified the fix for the cross-input-queue foreground acknowledgment race. The separate interaction suite passed all 27 checks. These fixture results do not establish accessibility compatibility with every third-party application.
