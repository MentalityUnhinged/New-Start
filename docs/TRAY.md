# Windows notification-area access

Windows Explorer owns third-party notification-area icons and their callback contracts. Shell_NotifyIcon lets an application register its own icon with Explorer; it does **not** provide a supported API to enumerate/rehost every other app's icons. Copying Explorer toolbar data, scraping process memory or rebroadcasting private callbacks would introduce fragile undocumented behaviour and security boundaries. New Start does not do that and does not display pretend tray icons.

The supported alternative is an explicitly labelled **Windows notification area** launcher, independently placed in Dock and AppBar. `NotificationTray.BuildButton(owner, prefs, revealNativeTray)` uses existing styling/context menus. The callback should request a temporary taskbar-suppression interaction lease (long enough for native tray interaction). The launcher resolves a verified Explorer-owned taskbar, waits for it to become visible, and requests foreground focus through Win32. The user then uses the **real** Windows notification icons, overflow, native status/tooltips, menus and left/right-click actions. Taskbar suppression must remain paused while the native taskbar/menu owns focus and resume once the user leaves it.

The launcher is not presented as an inline list of third-party icons. It prefers Explorer's primary taskbar, because secondary taskbars may not contain a notification area; if that is unavailable, it falls back to a verified taskbar on the current monitor. After the user clicks the launcher, it requests the documented Windows + B system action to focus the real notification area, including an auto-hidden taskbar. This is a known Windows command, not a guessed application shortcut. Explorer decides which icons, overflow and notification indicators are available. Windows may reject focus or visibility changes; the UI checks the resulting foreground and reports failure with normal taskbar settings/Windows-key access. No admin rights, process injection or icon-callback impersonation is used.

Independent Dock/AppBar switches refer to the launcher, so enabling both creates two access points without duplicating the notification-area icons themselves. Root integration should use the same visibility preferences in Standard and Advanced settings. The button has an accessible name, compact hit area, existing themed right-click actions and inherits foreground styling.

Source: [Shell_NotifyIcon](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw), [notification area guidance](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area), [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow), [documented Windows keyboard shortcuts](https://support.microsoft.com/en-us/accessibility/windows/keyboard-shortcuts-in-windows).

Validation must avoid clicking personal third-party icons or transmitting user data. Live multi-monitor overflow differences and activation policy need desktop acceptance; absence of a general supported enumeration API is an explicit platform limitation, not a claimed completed inline tray implementation.
